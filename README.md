# 作品名 The Dungeon

## 1. 基本情報
* **制作者氏名**: 中島響
* **制作期間**: 2025年8月 〜 2026年10月
* **コンセプト**: 「成長による探索の進展」と「資源収集ループ」を融合させたゲーム体験
* **開発言語/API**: C++20 / DirectX 12

---

## 2. 動作環境と起動・終了方法

### 動作環境
* **OS**: Windows 10 / 11 (64bit)
* **その他**: DirectX 12対応グラフィックボード

### 起動方法
* DirectX12.exeを実行してください。
* exeのあるフォルダから起動する必要があります。
* 起動に約7秒かかります。

### 終了方法
* ゲームプレイ中にウィンドウ右上の `×` ボタンで終了します。

---

## 3. ゲームの概要と遊び方
* **目的**: 迷宮を探索して資源を集め、キャラクターを強化しながら深層を目指します。
* **特徴**: 集めた資源を使って装備を購入し、自身の能力を拡張することで、前回は進めなかったエリアへ到達できるようになります。
* **ゲームプレイ動画**:　プレイ映像：https://youtu.be/ZdndqOTHrhM  
 　　　　　　　 エディタ紹介：https://youtu.be/-9arC9fHOSA  
 プレイ映像は開発途中のもので、現在はクリアまで実装されています。


* **ゲームの流れ**: 街→ダンジョン探索→帰還→町で強化→ダンジョン探索→...
* **ダンジョン探索**: ダンジョンはターン制で進行し、1回の行動のたびにAPを消費します。APがなくなると、強制的に帰還します。ダンジョンでは敵を倒すとGを取得し、採掘をすると魔鉱石という素材を取得できます。これらの素材を街で装備に変えて強化していきます。
* **クリア条件**:ダンジョンの深部に到達することでクリアです！
* **想定プレイ時間**:約1時間のプレイ時間を想定しています。こまめなセーブを推奨します。

## 5. ソースコードの見どころ

ソースコードは `DirectX12/scripts` を参照してください。`engine/`(描画・音声・入力・アセット管理などの汎用部分)と `game/`(街・ダンジョンのゲームロジック)に分けています。

**本作で最も力を入れたのは、DirectX12を独学で習得し、エンジン層からゲームロジックまでを一人で設計・実装したことです。** 描画APIの直接操作から、敵の行動制御やターン制御といったゲームの仕組みまで、計画を立てて段階的に作り上げました。

### 自分で実装した範囲

| 層 | 内容 |
|---|---|
| 描画(DX12) | デバイス・スワップチェーン・パイプライン構築、ポイントライト/スポットライト、炎のパーティクル、フェード演出(HLSL 11本)、Direct2D/DirectWriteによるテキスト描画 |
| エンジン基盤 | Actor / Component / Scene / SceneManager、JSONによるデータ駆動、ImGuiによるエディタ |
| 音声 | XAudio2による再生 |
| ゲームロジック | マップデータの読み込み、敵・資源のランダム生成、A*による経路探索、ターン制御、敵の行動制御、ミニマップ |

### 特にアピールしたい点
#### ① GPUリソースの空き領域管理(`engine/asset/AssetManager`)

**課題**: DX12では、コンスタントバッファとディスクリプタヒープの領域をアプリ側で管理する必要があります。オブジェクトごとに作成・破棄すると、生成コストがかかるという問題がありました。  
**方法**: 最初に大きな領域を確保し、ゲーム中は `AssetManager` が割り当てます。解放済み領域は `std::map<開始位置, サイズ>` で管理し、確保時は空き領域を優先的に再利用します。解放時は、直前・直後の空き領域と連続していれば結合します。これを `getCBEndIndex` / `getHeapEndIndex` / `deleteMemory` / `deleteHeap` として実装しています。  
**使い方**: `MeshComponent` / `SpriteComponent` / `TextComponent` などが、生成時に領域を確保し、破棄時に返却します。オブジェクトの寿命と領域の寿命が一致します。  
**キャッシュの実装**: 頂点バッファとテクスチャは、読み込み済みのものをキャッシュして使い回しています。

**処理時間の計測**: キャッシュとアロケータの効果を、Releaseビルドで3段階に切り替えて比較しました。

| 段階 | 内容 |
|---|---|
| 1 | 3Dオブジェクトの生成のたびに、頂点バッファ・テクスチャ・コンスタントバッファを作成 |
| 2 | 頂点バッファとテクスチャをキャッシュ(コンスタントバッファは個別作成) |
| 3 | 2に加えて、コンスタントバッファとヒープをアロケータで割り当て(現行) |

| 指標(平均) | 段階1 | 段階2 | 段階3 |
|---|---|---|---|
| 街→ダンジョンの遷移 | 11,938 ms | 111 ms | **53 ms** |
| 3Dオブジェクト100個の生成+削除 | 4,939 ms | 61.2 ms | **0.68 ms** |
| 3Dオブジェクト1000個の生成+削除 | 実行不可(VRAM不足) | 673 ms | **5.4 ms** |
| 起動時間 | **4.6 s** | 6.9 s | 7.0 s |
| 1000個生成後のプロセスメモリ | — | 865 MB | **713 MB(増加なし)** |

- **起動時間の内訳**: 現行の起動約7秒のうち、音声初期化が約4秒(全段階で同じ)、`AssetManager`初期化が約2.2秒です。現在の起動時の最大要因は音声初期化でした。
- **キャッシュ(段階1→2)**: 遷移時間が約100分の1になりました。代わりに、起動時にアセットを一括で読み込むため、起動が約2.3秒長くなりました。
- **アロケータ(段階2→3)**: 生成+削除が約90〜120倍速くなり、繰り返してもメモリが増えません。
- ダンジョン中のCPUフレーム時間は、どの段階も1 ms未満で、悪化はありません。
- 計測条件: Core i7-11370H / RTX 3050 Laptop、段階ごとに11回(初回を除く10回の平均)。段階の切り替えは3Dメッシュのみで、スプライトやテキストなどは全段階で現行のアロケータを使用。


#### ② Strategyパターンによる敵AI(`game/dungeon/enemy`)

**課題**: 敵の種類ごとに行動が違い、条件分岐で書くと、敵を足すたびにコードが肥大する問題点がありました。  
**方法**: 「移動」(`EnemyMoveStrategy`)と「攻撃」(`EnemyAttackStrategy`)を別々のStrategyにしました。移動は ランダム / A*による追跡 / 一定範囲のみ追跡 / ボスの挙動、攻撃は 近接攻撃 / 攻撃しない です。この2つを組み合わせて敵を構成します。
- 一定範囲を追跡する実装は A*による追跡 と ランダム移動 を内部に持ち、索敵範囲内ならA*で追跡、範囲外ならランダム移動します。
- 敵データ(`enemyData.json`)の `movePattern` / `attackPattern` の文字列から、名前→生成処理の対応表で生成します。  
**新しい行動パターンは、クラスを1つ書いて対応表に1行足すだけで追加できます。**
- ボスも同じ仕組みで実装しています(`BossPillarStrategy`)。
元の実装の問題点と、Strategyによる解決策は自分で考え、書き換えの作業量が多かったため、AIの支援を受けて移行しました。(8章参照)

#### ③ ステートマシンによるターン制御(`game/dungeon/turn`)

**課題**: プレイヤー入力、敵の行動、ターン終了処理、などの状態遷移をif文のみで実装すると、今の状態を追うことや新たな制御を追加するのが難しいという問題がありました。  
**方法**: `TurnStateMachine` が状態を管理します。各状態は `TurnState` を継承し、`update()` が遷移先の状態を返します(遷移しない場合は `nullptr`)。
- 流れ: プレイヤーのターン → 敵の行動 → ターン終了 → プレイヤーのターン。途中でゴール・死亡・AP切れ・帰還確認の各状態へ分岐します。
- ゴール・死亡・AP切れ・帰還の4状態は、共通の基底 `DungeonEndState` にウィンドウ表示とフェードアウトを持たせ、演出と遷移先だけを派生クラスで差し替えます。
元の実装の問題点と、状態ごとに責務を分ける設計は自分で考え、書き換えの作業はAIの支援を受けて行いました。(8章参照)

### 外部ライブラリの使い分け

- **自作**: レンダラ、アセット管理、シーン・コンポーネント構造、敵の行動制御、ターン制御  
- **外部ライブラリ**: stb_image(画像デコード)、stb_vorbis / minimp3(音声デコード)、nlohmann/json、ImGui、magic_enum(7章参照)

## 6. 改善点
### ① 責務の分離と依存関係の整理

**現状**: `Graphic` クラスが約1,800行あり、バッファ確保、パイプライン(PSO)生成、フェンス同期、コマンド管理、フェード処理までを担っています。`Game` も同様に多くの役割を持っています。また、`Scene` から `Game` や各Managerを取得でき、各Componentが `getScene().getGame().getAssetManager()` のように辿って使っているため(`getGame()` の呼び出しは約180箇所)、依存関係が複雑になっています。  
**問題**: 変更の影響範囲が読みにくく、機能単位でのテストや差し替えが困難です。  
**改善方針**:
- `Graphic` を、バッファ/リソース生成、PSO生成、フェンス、コマンド管理に分割する。
- 必要なものだけをコンストラクタで渡す(依存性注入)ようにして、Managerへの連鎖的なアクセスをなくす。  
- ゲーム側がDirectX12などの低レイヤーAPIに触れなくて済むよう、エンジンとゲームの境界を明確にする。  

### ② CPUとGPUの同期点の削減

**現状**: フレーム描画はCPUとGPUを非同期に進めていますが、次の箇所で、CPUがGPUの完了を待っています。
- テクスチャ読み込み(`Graphic::createShaderResource`)は、1枚ごとにコピーを実行し、フェンス完了を `WaitForSingleObject` で待ちます。ロード用コマンドアロケータが1つのため、完了を待たないと再利用できない構造です。
- テキストの変更時、テキストの描画が終わるまでCPUが待機します。
**問題**: 起動時のアセット一括ロードの時間が、読み込む枚数に比例して伸びます。テキストの更新があるフレームではCPUが止まり、非同期処理の利点が活かせていません。
**改善方針**:
- 複数テクスチャのアップロードを1つのコマンドリストにまとめ、フェンス待ちを1回にする。
- テキスト用のテクスチャをフレームインフライト数(本ゲームでは2枚)だけ持ち、内容が変わったときだけ更新する。

## 8. AIの使用について
開発にはAIを補助として使用しました。設計上の問題点の発見と解決策の立案は自分で行い、調べものや作業量の多い部分でAIの支援を受けています。使い方は開発の時期によって変わりました。

### 使い方の変遷

| 時期 | 内容 | AIの使い方 |
|---|---|---|
| 初期 | DirectX12の初期化、モデルの描画、メインループ、Actorなど | 書籍とWebサイトを参考に、自分で実装。AIはエラーの調べものに使用 |
| 中期 | ゲームロジックなどの実装 | 実装方法をAIに相談して案を出してもらい、採用を自分で判断して実装。一部(OGGファイルのデコード処理など)は、AIが提示したコードを使用 |
| 直近 | ファイル整理、敵・ターン制御のリファクタリング | Claude Codeに直接書かせ、結果を自分で確認 |

### 用途別

| 用途 | 使用したAI | 内容 | 自分が担った部分 |
|---|---|---|---|
| スプライト画像の生成 | Gemini、Claude | ゲーム内のスプライト画像を生成 | 使用する画像の選定、ゲームへの組み込み |
| 3Dモデルの生成 | Claude(Blender拡張) | 3Dモデルを生成 | モデルの選定、ゲームへの組み込み |
| 実装方法の調査 | Claude | 実現方法や既存技術の候補出し | 候補の比較、採用の判断、実装 |
| ファイル整理 | Claude Code | `engine/` `game/` フォルダへのファイル移動 | フォルダ構成の方針決定 |
| リファクタリング | Claude Code | 敵の行動とターン制御を、Strategyパターン/ステートマシンへ書き換える作業 | 元の実装、問題点の分析、解決策の設計、動作確認 |
| 資料作成 | Claude | READMEなどの文章作成、添削 | 自身のアピールポイントや改善点の提示 |  
| 計測用コード | Claude Code | アロケータとキャッシュの実装による処理時間の違いを計測するためのコード生成 | 計測区間や比較対象の指定 |

描画(DirectX12)、アセット管理(アロケータ)、エンジン基盤、ゲームロジックの実装は自分で行いました。敵の行動とターン制御も、元の実装は自分で書いています。
